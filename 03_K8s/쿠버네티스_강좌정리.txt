 //////////////////////////////
 1장 K8s (Kubernetes) 개요
 //////////////////////////////
 
   1.개념
     - 오픈소스 시스템.
	 - Docker같은 컨테이너 포함하는 Pod를 관리(생성/사용/종료/배포)하는 시스템의 표준 
 	   (오케스트레이션 역할)
	   
	    https://kubernetes.io/
	 
   2.  특징
     - 어플리케이션 부하에 따른 자동 배포 기능 
	 - 쉬운 scaling과 Load Balancing (요청분배)
	 - 자동으로 네트워크 구성 
	 - 문제 발생 시 컨테이너 자동 재시작 및 재배치
	 - 필요시 이전버전으로 롤백.( 바로이전, 특정버전 롤백 가능)
	 - 표준이기 때문에 어떤 클라우드와도 연동 가능  (AWS, Azure(MS), GCP(Google))
	 
   3. K8s 아키텍처
     
	 https://kubernetes.io/ko/docs/concepts/architecture/
	 
	   k8s  클러스터
	   --------------------------------------------
	   
	     Control Plane          -------------->   Data plane         
		 (Master node:노트북1)					  ----------------
											       Worker Node (노트북2) ex. App Pod 
												   
												   ..
												   
												   Worker Node ( 노트북3) ex. DB Pod
												   
		--------------------------------------------										   
      
    Control Plane  역할: 관리자 역할.
	Worker Node: 실제 컨테이너를 실행하는 서버.
	  
	 4. 클러스터
	 
	   1)개념
	    - 여러 대의 컴퓨터(노드)를 하나의 컴퓨터처럼 동작하도록 구축한 시스템의미.
		
	   2) 필요성	
	   
	     - 1대 운영시
		    서비스 장애 발생시 바로 서비스 종료.
		 
		 -클러스터 운영시
		    여러 노드에 분산 배치 가능.
			장애 발생 시 다른 노드로 재배치
			트래픽 증가 시 요청분배 가능.
			
			
	   3) 노드 (Node)
	   
	      가. 개념
		    - 클러스터를 구성하는 컴퓨터 의미. 
			
		  나. 종류
		  
		     a. Control plane ( master node )
			   - 클러스터 전체를 관리하는 역할.
			   - 구성요소 4가지
			     > kube-api-server: Worker node의 kubelet과 연동.
			     > scheduler : Pod를 어느 노드에 배포할 지 결정.
				 > controller-manager: worker 노드에 있는 pod 복구 담당 ( pod 갯수등 참고)
				 > etcd : 클러스터의 상태 정보 저장소.
				 
			 b.  Data Plane ( worker node )
			   - 실제 기능을 가진 Pod가 실행하는 역할.
			   - 구성요소	 3가지
			     > kubelet : Master node와 통신 담당.
				 > CRI(Container Runtime Interface): Pod(컨테이너)를 실행하는 런타임.
				                                     containerd
													 
				 > kube-proxy: Node와 Pod등에서 사용하는 네트워트 통신 담당.									 

 --------------------------------------------------------------
   5. Control plane ( Master node )
			   
	 1) 개념.
       - 클러스터 전체를 관리하는 역할의 서버.

     2) 구성요소 4가지
 
       가. API Server
			- K8s 외부에 노출하는 구성요소, 모든 작업의 진입점(entry point) 역할 담당.
			- 사용자가 요청하는 명령어(kubectl)를 가장 먼저 받아서 처리함.
			
	   나. Scheduler
	        - Pod를 어떤 노드에 배치할 지를 결정.
			- 노드의 CPU/Memroy 자원 사용량 및 규칙(ex. 특정노드에서만 배포)을 고려해서 
			  적합한 노드를 선택함.
			  
	   다. Controller Manager
		  - 클러스터의 상태를 원하는 상태(desired state)로 유지하기 위해서 사용하는 구성요소.
    		즉, 문제가 있어서 종료된 Pod를 다시 복구함.  
		  - desired state 를 맞추기 위한 다양한 XXXController 들이 동작함.
		  
		      node controller: 노드 상태 관리 
			  ..
			  
		==> 클러스터가 원하는 상태를 맞춰줌.
		
	   라. Etcd
	     
		 - 클러스터의 상태 정보 저장소.
		 - key/value 형식
		 - 대표적으로 pod, service, replicaset, configmap 등 리소스 정보를 저장/관리.
		 
	------------------------------------------------------------------------------	 
   6. Workd node

      1)개념.
	    - 실제 컨테이너를 포함하는 Pod가 실행되는 곳.
		
	  2) 구성요소
	  
	    가. kubelet
			-Master node의 API Server 와 통신 담당.
			- 주로 Worker node의 상태정보(pod 등 여러 리소스 상태)를 
			    master node에게 전달함.
			
		나. kube-proxy
		     - Node와 Pod등에서 사용하는 네트워트 통신 담당.	
		
		다. CRI( containerd )
	       - CRI(Container Runtime interface)이고 컨테이너를 실행하는 스펙을 정의한 개념.
		     ( 자바의 인터페이스와 비슷 )
			 실제 구현한 구현물: containerd, CRI-O 등.
			 
		   - 용도: 컨테이너를 실행하는 런타임 환경을 제공.
		         즉 컨테이너를 생성하기 위한 이미지 다운로드
				   컨테이너 생성/중지/삭제 등.

 //////////////////////////////
 3장 kubectl 
 //////////////////////////////	
 https://kubernetes.io/docs/reference/kubectl/
 
   1. 개요
      
	  - K8s 클러스터를 관리(제어)하는 명령어.(CLI 기반)
	  - K8s 설치하면 자동으로 설치됨.
	  - Master Node의 API Server와 통신
	  
	              kubectl get nodes
				  (실제 REST API 형태로 요청 )
	      사용자 ---------------------> API Server ----> 처리
    
	2. 문법
	
	   kubectl [command] [TYPE] [NAME] [flags]
	 
	 
	    command: 리소스(pod,service,..)에 대해서 수행할 동작 지정.
		        ex. get : 리소스 조회
				   delete : 리소스 삭제
				   describe: 상세 정보 조회
				   apply: 리소스 생성/수정
				   logs: 로그 확인
				   exec: 컨테이너 접속/명령어 실행
				   rollout : 배포관리( 롤백 포함)
				   config: 클러스터 접속관리 ( 로컬/클라우드)
				   
				   
		TYPE:  대상이 되는 리소스 종류 ( 대소문자 구별안함,  단수/복수/약어 모두 가능 )
		
		     확인방법 : kubectl api-resources
			 
			 ex. pod, pods ,po 모두 가능
			 
	
	    NAME: 리소스명 ( 대소문 구별함. name을 지정하지 않으면 모든 리소스 의미)
		
		    ex.  kubectl get pods            <=== select * from table;
                 
                 kubectl get pods  my-pod    <=== select * from table where ~ ;
				 
		flags: 옵션
		      ex.  -f : 파일 지정.
			       --all: 모든것 의미. ex.  kubectl delete all --all
				   -it : 인터렉티스 접속.
				   ..

 //////////////////////////////
 4장 kubeconfig 개요 
 //////////////////////////////	
  
    1)개념
	   - kubectl 클러스터에 접속하기 위해서 사용하는 설정파일임.
	   - 윈도우: C:\Users\User\.kube\config 에 저장되어 있음. ( 나중에 AWS 클러스터 추가하면 이 파일에 추가됨 )
	     리눅스:  .kube/config
		 
	2) 구성요소 3가지 
	
	  가. cluster
			- 접속할 K8의 클러스터 정보가 저장됨.
			  ex. API Sever 주소, 클러스터 이름.
			  
	  나. context
		 - cluster와 user 정보를 연결한 설정.
		  즉, 누가(user) 어떤 클러스터(cluster)를 접속할지를 설정.
	  
	  
	  다. user
	       - 접속할 사용자 정보.
		    ex. 사용자명, 인증정보 등
			

	3. 특징
	   - 여러 클러스터 정보 저장이 기능.
	   - 여러 사용자 정보 저장이 가능.
	   
	   
	4. config 주요 명령어. 
	   https://kubernetes.io/docs/reference/kubectl/generated/kubectl_config
	   
	     kubectl - kubectl controls the Kubernetes cluster manager
		kubectl config current-context - Display the current-context
		kubectl config delete-cluster - Delete the specified cluster from the kubeconfig
		kubectl config delete-context - Delete the specified context from the kubeconfig
		kubectl config delete-user - Delete the specified user from the kubeconfig
		kubectl config get-clusters - Display clusters defined in the kubeconfig
		kubectl config get-contexts - Describe one or many contexts
		kubectl config get-users - Display users defined in the kubeconfig
		kubectl config rename-context - Rename a context from the kubeconfig file
		kubectl config set - Set an individual value in a kubeconfig file
		kubectl config set-cluster - Set a cluster entry in kubeconfig
		kubectl config set-context - Set a context entry in kubeconfig
		kubectl config set-credentials - Set a user entry in kubeconfig
		kubectl config unset - Unset an individual value in a kubeconfig file
		kubectl config use-context - Set the current-context in a kubeconfig file
		kubectl config view - Display merged kubeconfig settings or a specified kubeconfig file
		
		
	 ex.   
	 
	     1) cofing 파일 내용 조회 
	 
	       kubectl config view  # 민감정보 출력안됨.   
	       kubectl config view  --raw  # 민감정보 출력됨 
		   
		 2) 현재 사용중인 컨텍스트 
		 
		   kubectl config current-context
		     ddocker-desktop
			 
	    3) 현재 등록된 모든 컨텍스트 정보 조회
		
		  kubectl config get-contexts
		  
		    CURRENT   NAME             CLUSTER          AUTHINFO         NAMESPACE
			*         docker-desktop   docker-desktop   docker-desktop

 5장  K8s 의 Configuration 설정 방법
 //////////////////////////////	
  
     1) 개념
	   - K8s에 리소스(Pod,  Service ,.... )등을 어떻게 생성할 것인지를 정의하고 관리하는 방식관련 내용임.
	   
	   
	 2) 방법 2가기
	 
	   가. 명령형 구성 방법 ( Imperative Configuration )
	       -시스템에 직접 명령어 입력하는 방식.
		    ex.  docker run -p 8080:80 nginx
			     kubectl run nigix
		   -장점:
		     즉각적으로 실행가능
			 직관적임.
			 
		   -단점:
		      문서화하 안되어 있기 때문에 이력관리가 안됨.
			  재현성 떨어짐.
	   
	   나. 선언형 구성 방법 ( Declarative Configuration )
	       - yaml 파일에 클러스터에 구축하고자 하는 원하는 상태(desired state)를 코드화하는 방법.
		   
		   -장점:
		      문서화 되어 있어서 이력관리 가능함. 
			  재현성 향상.
			  대규모 운영에 유리.
		   
-------------------------------------------------------------------------------------------------	   

    3) K8s 의 YAML ( Yet Another Markup Language,  manifest 파일이라고도 부름. )
	 
	   가. 개념
	     - K8s의 클러스터가 원하는 상태 ( Desired State)를 갖도록 설정하는 파일임 (*********************)
		 
		 
	   나. 공통 구조 
	   
	         apiVersion: v1	| apps/v1 		# API 버전,  확인방법: kubectl api-resources , kubectl api-versions
			 kind: Pod | Deployment			# 생성하려는 리소스 종류 ex. Pod, Service, Deployment ,.....
						                      대소문자 구별됨.
			 metadata:						# kind의 추가 설정정보.
											  ex. 이름,라벨, 네임스페이스
			 
			 spec:							# 리소스마다 다름. 개별적인 리소스마다 정리 필요.
			 
			 
	   다. YAML 작성 가이드 
	   
    	   각 리소스마다 yaml 내용은 	 https://kubernetes.io/docs/home/ 검색해서 복사/붙이기 해서 사용함.
		   
		    또는
			
			kubectl explain pod  # pod에 대한 소개 및 필드(field) 소개
			
			kubectl explain pod.spec  # pod의 spec 소개 
			
		    kubectl explain pod.spec.containers  # pod의 spec 소개 
			
			
	  다. kubectl 과 yaml 처리
	  
	    - 동작방식
		
				     	pod.yaml --> JSON -------->
		   kubectl -------------------------------->  API Server
	      (pod.yaml)

 6장  K8s 주요 객체 1 - Pod
 //////////////////////////////	
  
     1.개념
	   - K8s 에서 관리(생성/수정/삭제)하는 최소 단위임 (  docker에서는 컨테이너가 최소 단위였음 )
	   - Pod 안에 하나 이상의 컨테이너를 포함함. ( 일반적으로 하나의 컨테이너를 가짐 )
	   
	     https://kubernetes.io/docs/concepts/workloads/pods/
		 https://kubernetes.io/docs/reference/kubernetes-api/core/pod-v1/
  
     2. 특징
	   a. Pod 안에 하나 이상의 컨테이너를 포함함.
	   b. Pod 안에 있는 컨테이너들이 네트워크과 볼륨을 공유할 수 있음. (************)
	   
			--------------------------
			  pod 
			  
			   --------------
			    conainter1
			   --------------

			   --------------
				container2
			   --------------
			   
			   shared Network
			   shared Volume
			----------------------------------
			
		c. Pod는 일시적인 ( Ephemeral ) 객체임 (영구적인 객체가 아님 ) 
		  언제든지 제거될 수 있고 새로운 Pod가 생성될 수 있음.
			 ex.  Node 장애
			      Pod 삭제
				  Deployment 업데이트
				  Scale Out/In  ( 트래픽에 따른 Pod 갯수 증가/감소 )
				  
		  ==> Pod에서 했던 데이터 유지가 기본적으로 불가. ( 영속성을 위해서 Volume 사용함 )		 
		
		d. Pod는 직접 생성하기 보다는 다른 리소스를 이용해서 만드는것이 일반적임.
		   이유는 더 많은 기능이 포함됨.
			ex. Deployment, StatefulSet, Job, CronJob
		   
		   
		e.  Pod는 lifecycle 가짐.
		https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/
		
		     pending --> running --> succeeded/failed
			 
		  pending: Pod가 생성되었으나 아직 실행되지 않음.
		  running: 하나이상의 컨테이너가 실행중.
		  succeeded: 하나이상의 컨테이너가 모두 정상종료.
		  failed:   하나이상의 컨테이너가 비정상종료.
		  Unknown:  노드와 통신불가로 인해서 상태확인 불가.
		  
		  
		  확인방법:  kubectl get pods 
		  
		f. RestartPolicy 정책이 있음.
		  - Pod가 제거된 후 재시작과 관련된 정책임.
		  https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#example-scenarios
		  
		  
		   가. Always : 컨테이너가 종료되면 항상 재사작됨. 
		   나. OnFailure : 실패했을때만 재시작. 
		   다. Never   : 재시작하지 않음.
		   
		  
		g. image관련 정책 (  ImagePullPolicy )
 
     https://kubernetes.io/docs/concepts/containers/images/#image-pull-policy
	 
	        - Pod가 실행될 때, 컨테이너 이미지를 언제, 어떤 방식으로 hub에서 가져올지 결정하는 정책임.
	    
			- 3가지
			
			 가.  Always : 무조건 매번 hub에서 가져옴.( 사실은 아님 )
						   실제동작은 다음과 같다.
						   -hub에 이미지 확인을 요청함.
						    만약에 로컬에 없으면 새롭게 다운로드  되고
							있으면 캐시 이미지 사용.
			 
			 나.  IfNotPresent : Node(local)에 이미지막 없을때만 다운로드  ( 가장 많이 사용 )
			 
			 다.  Never  : 항상 로컬에 있는 이미지 사용.
		
		
		    - ImagePullPolicy를 생략했을 경우의 기본값.
			
			   가. tag가 latest 인 경우 
				- 기본적으로 Always로 동작됨.
			   
			   나. tag가 특정 버전인 경우 ( latest가 아닌 경우 )
			    - 기본적으로 IfNotPresent 동작됨.
				
		
			- ImagePullBackOff
			 https://kubernetes.io/docs/concepts/containers/images/#imagepullbackoff
			 
			  ==> K8s가 이미지를 가져오지 못하는 경우에 발생됨. 결국 컨테이너가 생성되지 못함.
			  ==> 원인: 이미지 이름 오타.
					    tag 오타

	3) Pod 상세 보기 
	
	 https://kubernetes.io/docs/reference/kubectl/generated/kubectl_describe/
	 
	  -개념:  리소스의 상세 정보를 출력하는 명령어. ( docker describe , docker inspect 비슷 )
	  
	  - 문법:
	        kubectl describe (-f FILENAME | TYPE [NAME_PREFIX | -l label] | TYPE/NAME)
	   
	   
	   ex. 
	        kubectl describe pods   # TYPE
			
			kubectl describe pods/nginx  # TYPE/NAME
			
			kubectl describe pods -l name=myLabel
			
	
	- 살펴봐야된 항목은 Event 항목임 
	
	     a. pending: CPU 나 Memory 자원부족인 경우에 주로 발생됨.
		 
		 b. ImagePullBackOff :  컨테이너를 생성할 이미지가 없는 경우.
							   ex. 이미지명 오타, tag 오타.
							   
		 
		 c. CrashLoopBackOff : 컨테이너가 계속 죽고 살아나는 동작을 반복함.
							 ex. 어플리케이션 오류
							     환경변수 설정 오류 
								 포트 충돌

	4) Pod 삭제 
	https://kubernetes.io/docs/reference/kubectl/generated/kubectl_delete/
	
	  - 개념: 리소스 삭제하는 명령어. 
	  
	  -문법 : 
	    
		  kubectl delete ([-f FILENAME] | [-k DIRECTORY] | TYPE [(NAME | -l label | --all)])
		  
		  --all : 모든 리소스 삭제 , ex.  kubectl delete pods --all
		  -f 파일명: 파일안에 지정된 리소스를 삭제.

		ex.

		   kubectl delete -f 파일명.yaml
		   
		   kubectl delete pod,service baz foo
		   kubectl delete pods,services -l name=myLabel
		   
		   kubectl delete pods --all
		  
	==> 이미지는 삭제 안됨. 명시적으로 삭제해야 됨.

	5) Pod 내의 컨테이너에서 실행되는 어플리케이션(ex. SpringBoot) 로그 출력
	
	  https://kubernetes.io/docs/reference/kubectl/generated/kubectl_logs/
	  
	   - 개념: 컨테이너에서 실행되는 어플리케이션(ex. SpringBoot)의 정상로그(표준출력)와 오류로그(표준에러)를 출력하는 명령어.
	   
	   - 문법: 
	
	          kubectl logs [-f] [-p] (POD | TYPE/NAME) [-c CONTAINER]
	
				-f, --follow : 인텔리제이 로그처럼 실시간으로 로그 출력 가능.
				-c 컨네이너명:  컨테이너명 지정.
	            --tail n :     마지막 로그중 n개 출력.
				-l, --selector string : 필터링 
				--since 시간:  지정된 시간 이후 로그만 출력, ( 단위: 2s, 2m, 2h )
				--timestamps : 시간 출력
				-p, --previous : 재시작전 로그 출력.  ex. CrashLoopBackOff 발생시 필수로 봐야됨. 
		  ex. 
		      kubectl logs nginx-pod		
			  kubectl logs nginx-pod	--tail 10
              kubectl logs nginx-pod    --since=1m
			  kubectl logs nginx-pod   -c  nginx-container
			  
		==> 최종적으로 정리
		 
		     kubectl get : 상태 확인용.
			 kubectl describe: 이벤트 확인용
			 kubectl logs : 우리가 사용하는 어플리케이션(ex. Springboot, Vuejs ) 로그값 출력.

	8) Label CRUD		 
https://kubernetes.io/docs/reference/kubectl/generated/kubectl_label/
	
	   - 개념: label을 추가/수정/삭제/조회 하는 명령어
	   
	   - 문법:
             kubectl label [--overwrite] (-f FILENAME | TYPE NAME) KEY_1=VAL_1 ... KEY_N=VAL_N [--resource-version=version]
   	   
		    --overwrite: 기존 라벨 덮어쓰기 ( 수정 )
			--all:  모든 리소스 선택.
			
			        ex.  kubectl label pods --all  key=value
	   
	        -f, --filename 파일명: 지정된 파일에 라벨 추가 .
			--list : 라벨 출력
			key-   : 라벨삭제  ex. app- ,  env-
			
	     		
		 ex. 
		  
		    kubectl label pods nginx-pod unhealthy=true  # 추가 
			 kubectl label pods --all status=unhealthy   # 모든 pod 추가 
			 
			kubectl label --overwrite pods nginx-pod status=unhealthy  # 수정
			
	         kubectl label pods nginx-pod  app-    # app 라벨
				
			 # 라벨 조회 
			 kubectl label pods  nginx-pod  --list  # 라벨 출력
			 kubectl get pods --show-labels    #  라벨 출력 
			 
			 kubectl get pods  -L app,env     # 지정된 라벨 출력, 공백없이 지정.
			 kubectl get pods  -l app=nginx     # 지정된 라벨에 해당하는 Pod 정보 출력
			 
			kubectl get pods  -o yaml   # lable 출력됨 
			kubectl get pods  -o json   # lable 출력됨
