 //////////////////////////////
 1장 K8s (Kubernetes) 개요
 //////////////////////////////
 
   1.개념
     - 오픈소스 시스템.
	 - Docker같은 컨테이너 포함하는 Pod를 관리(생성/사용/종료/배포)하는 시스템의 표준 
 	   (오케스트레이션 역할)
	   
	    https://kubernetes.io/
	 
   2.  특징
     - 어플리케이션 부하에 따른 자동 배포 기능 
	 - 쉬운 scaling과 Load Balancing (요청분배)
	 - 자동으로 네트워크 구성 
	 - 문제 발생 시 컨테이너 자동 재시작 및 재배치
	 - 필요시 이전버전으로 롤백.( 바로이전, 특정버전 롤백 가능)
	 - 표준이기 때문에 어떤 클라우드와도 연동 가능  (AWS, Azure(MS), GCP(Google))
	 
   3. K8s 아키텍처
     
	 https://kubernetes.io/ko/docs/concepts/architecture/
	 
	   k8s  클러스터
	   --------------------------------------------
	   
	     Control Plane          -------------->   Data plane         
		 (Master node:노트북1)					  ----------------
											       Worker Node (노트북2) ex. App Pod 
												   
												   ..
												   
												   Worker Node ( 노트북3) ex. DB Pod
												   
		--------------------------------------------										   
      
    Control Plane  역할: 관리자 역할.
	Worker Node: 실제 컨테이너를 실행하는 서버.
	  
	 4. 클러스터
	 
	   1)개념
	    - 여러 대의 컴퓨터(노드)를 하나의 컴퓨터처럼 동작하도록 구축한 시스템의미.
		
	   2) 필요성	
	   
	     - 1대 운영시
		    서비스 장애 발생시 바로 서비스 종료.
		 
		 -클러스터 운영시
		    여러 노드에 분산 배치 가능.
			장애 발생 시 다른 노드로 재배치
			트래픽 증가 시 요청분배 가능.
			
			
	   3) 노드 (Node)
	   
	      가. 개념
		    - 클러스터를 구성하는 컴퓨터 의미. 
			
		  나. 종류
		  
		     a. Control plane ( master node )
			   - 클러스터 전체를 관리하는 역할.
			   - 구성요소 4가지
			     > kube-api-server: Worker node의 kubelet과 연동.
			     > scheduler : Pod를 어느 노드에 배포할 지 결정.
				 > controller-manager: worker 노드에 있는 pod 복구 담당 ( pod 갯수등 참고)
				 > etcd : 클러스터의 상태 정보 저장소.
				 
			 b.  Data Plane ( worker node )
			   - 실제 기능을 가진 Pod가 실행하는 역할.
			   - 구성요소	 3가지
			     > kubelet : Master node와 통신 담당.
				 > CRI(Container Runtime Interface): Pod(컨테이너)를 실행하는 런타임.
				                                     containerd
													 
				 > kube-proxy: Node와 Pod등에서 사용하는 네트워트 통신 담당.									 

 --------------------------------------------------------------
   5. Control plane ( Master node )
			   
	 1) 개념.
       - 클러스터 전체를 관리하는 역할의 서버.

     2) 구성요소 4가지
 
       가. API Server
			- K8s 외부에 노출하는 구성요소, 모든 작업의 진입점(entry point) 역할 담당.
			- 사용자가 요청하는 명령어(kubectl)를 가장 먼저 받아서 처리함.
			
	   나. Scheduler
	        - Pod를 어떤 노드에 배치할 지를 결정.
			- 노드의 CPU/Memroy 자원 사용량 및 규칙(ex. 특정노드에서만 배포)을 고려해서 
			  적합한 노드를 선택함.
			  
	   다. Controller Manager
		  - 클러스터의 상태를 원하는 상태(desired state)로 유지하기 위해서 사용하는 구성요소.
    		즉, 문제가 있어서 종료된 Pod를 다시 복구함.  
		  - desired state 를 맞추기 위한 다양한 XXXController 들이 동작함.
		  
		      node controller: 노드 상태 관리 
			  ..
			  
		==> 클러스터가 원하는 상태를 맞춰줌.
		
	   라. Etcd
	     
		 - 클러스터의 상태 정보 저장소.
		 - key/value 형식
		 - 대표적으로 pod, service, replicaset, configmap 등 리소스 정보를 저장/관리.
		 
	------------------------------------------------------------------------------	 
   6. Workd node

      1)개념.
	    - 실제 컨테이너를 포함하는 Pod가 실행되는 곳.
		
	  2) 구성요소
	  
	    가. kubelet
			-Master node의 API Server 와 통신 담당.
			- 주로 Worker node의 상태정보(pod 등 여러 리소스 상태)를 
			    master node에게 전달함.
			
		나. kube-proxy
		     - Node와 Pod등에서 사용하는 네트워트 통신 담당.	
		
		다. CRI( containerd )
	       - CRI(Container Runtime interface)이고 컨테이너를 실행하는 스펙을 정의한 개념.
		     ( 자바의 인터페이스와 비슷 )
			 실제 구현한 구현물: containerd, CRI-O 등.
			 
		   - 용도: 컨테이너를 실행하는 런타임 환경을 제공.
		         즉 컨테이너를 생성하기 위한 이미지 다운로드
				   컨테이너 생성/중지/삭제 등.

 //////////////////////////////
 3장 kubectl 
 //////////////////////////////	
 https://kubernetes.io/docs/reference/kubectl/
 
   1. 개요
      
	  - K8s 클러스터를 관리(제어)하는 명령어.(CLI 기반)
	  - K8s 설치하면 자동으로 설치됨.
	  - Master Node의 API Server와 통신
	  
	              kubectl get nodes
				  (실제 REST API 형태로 요청 )
	      사용자 ---------------------> API Server ----> 처리
    
	2. 문법
	
	   kubectl [command] [TYPE] [NAME] [flags]
	 
	 
	    command: 리소스(pod,service,..)에 대해서 수행할 동작 지정.
		        ex. get : 리소스 조회
				   delete : 리소스 삭제
				   describe: 상세 정보 조회
				   apply: 리소스 생성/수정
				   logs: 로그 확인
				   exec: 컨테이너 접속/명령어 실행
				   rollout : 배포관리( 롤백 포함)
				   config: 클러스터 접속관리 ( 로컬/클라우드)
				   
				   
		TYPE:  대상이 되는 리소스 종류 ( 대소문자 구별안함,  단수/복수/약어 모두 가능 )
		
		     확인방법 : kubectl api-resources
			 
			 ex. pod, pods ,po 모두 가능
			 
	
	    NAME: 리소스명 ( 대소문 구별함. name을 지정하지 않으면 모든 리소스 의미)
		
		    ex.  kubectl get pods            <=== select * from table;
                 
                 kubectl get pods  my-pod    <=== select * from table where ~ ;
				 
		flags: 옵션
		      ex.  -f : 파일 지정.
			       --all: 모든것 의미. ex.  kubectl delete all --all
				   -it : 인터렉티스 접속.
				   ..

 //////////////////////////////
 4장 kubeconfig 개요 
 //////////////////////////////	
  
    1)개념
	   - kubectl 클러스터에 접속하기 위해서 사용하는 설정파일임.
	   - 윈도우: C:\Users\User\.kube\config 에 저장되어 있음. ( 나중에 AWS 클러스터 추가하면 이 파일에 추가됨 )
	     리눅스:  .kube/config
		 
	2) 구성요소 3가지 
	
	  가. cluster
			- 접속할 K8의 클러스터 정보가 저장됨.
			  ex. API Sever 주소, 클러스터 이름.
			  
	  나. context
		 - cluster와 user 정보를 연결한 설정.
		  즉, 누가(user) 어떤 클러스터(cluster)를 접속할지를 설정.
	  
	  
	  다. user
	       - 접속할 사용자 정보.
		    ex. 사용자명, 인증정보 등
			

	3. 특징
	   - 여러 클러스터 정보 저장이 기능.
	   - 여러 사용자 정보 저장이 가능.
	   
	   
	4. config 주요 명령어. 
	   https://kubernetes.io/docs/reference/kubectl/generated/kubectl_config
	   
	     kubectl - kubectl controls the Kubernetes cluster manager
		kubectl config current-context - Display the current-context
		kubectl config delete-cluster - Delete the specified cluster from the kubeconfig
		kubectl config delete-context - Delete the specified context from the kubeconfig
		kubectl config delete-user - Delete the specified user from the kubeconfig
		kubectl config get-clusters - Display clusters defined in the kubeconfig
		kubectl config get-contexts - Describe one or many contexts
		kubectl config get-users - Display users defined in the kubeconfig
		kubectl config rename-context - Rename a context from the kubeconfig file
		kubectl config set - Set an individual value in a kubeconfig file
		kubectl config set-cluster - Set a cluster entry in kubeconfig
		kubectl config set-context - Set a context entry in kubeconfig
		kubectl config set-credentials - Set a user entry in kubeconfig
		kubectl config unset - Unset an individual value in a kubeconfig file
		kubectl config use-context - Set the current-context in a kubeconfig file
		kubectl config view - Display merged kubeconfig settings or a specified kubeconfig file
		
		
	 ex.   
	 
	     1) cofing 파일 내용 조회 
	 
	       kubectl config view  # 민감정보 출력안됨.   
	       kubectl config view  --raw  # 민감정보 출력됨 
		   
		 2) 현재 사용중인 컨텍스트 
		 
		   kubectl config current-context
		     ddocker-desktop
			 
	    3) 현재 등록된 모든 컨텍스트 정보 조회
		
		  kubectl config get-contexts
		  
		    CURRENT   NAME             CLUSTER          AUTHINFO         NAMESPACE
			*         docker-desktop   docker-desktop   docker-desktop

 5장  K8s 의 Configuration 설정 방법
 //////////////////////////////	
  
     1) 개념
	   - K8s에 리소스(Pod,  Service ,.... )등을 어떻게 생성할 것인지를 정의하고 관리하는 방식관련 내용임.
	   
	   
	 2) 방법 2가기
	 
	   가. 명령형 구성 방법 ( Imperative Configuration )
	       -시스템에 직접 명령어 입력하는 방식.
		    ex.  docker run -p 8080:80 nginx
			     kubectl run nigix
		   -장점:
		     즉각적으로 실행가능
			 직관적임.
			 
		   -단점:
		      문서화하 안되어 있기 때문에 이력관리가 안됨.
			  재현성 떨어짐.
	   
	   나. 선언형 구성 방법 ( Declarative Configuration )
	       - yaml 파일에 클러스터에 구축하고자 하는 원하는 상태(desired state)를 코드화하는 방법.
		   
		   -장점:
		      문서화 되어 있어서 이력관리 가능함. 
			  재현성 향상.
			  대규모 운영에 유리.
		   
-------------------------------------------------------------------------------------------------	   

    3) K8s 의 YAML ( Yet Another Markup Language,  manifest 파일이라고도 부름. )
	 
	   가. 개념
	     - K8s의 클러스터가 원하는 상태 ( Desired State)를 갖도록 설정하는 파일임 (*********************)
		 
		 
	   나. 공통 구조 
	   
	         apiVersion: v1	| apps/v1 		# API 버전,  확인방법: kubectl api-resources , kubectl api-versions
			 kind: Pod | Deployment			# 생성하려는 리소스 종류 ex. Pod, Service, Deployment ,.....
						                      대소문자 구별됨.
			 metadata:						# kind의 추가 설정정보.
											  ex. 이름,라벨, 네임스페이스
			 
			 spec:							# 리소스마다 다름. 개별적인 리소스마다 정리 필요.
			 
			 
	   다. YAML 작성 가이드 
	   
    	   각 리소스마다 yaml 내용은 	 https://kubernetes.io/docs/home/ 검색해서 복사/붙이기 해서 사용함.
		   
		    또는
			
			kubectl explain pod  # pod에 대한 소개 및 필드(field) 소개
			
			kubectl explain pod.spec  # pod의 spec 소개 
			
		    kubectl explain pod.spec.containers  # pod의 spec 소개 
			
			
	  다. kubectl 과 yaml 처리
	  
	    - 동작방식
		
				     	pod.yaml --> JSON -------->
		   kubectl -------------------------------->  API Server
	      (pod.yaml)

 6장  K8s 주요 객체 1 - Pod
 //////////////////////////////	
  
     1.개념
	   - K8s 에서 관리(생성/수정/삭제)하는 최소 단위임 (  docker에서는 컨테이너가 최소 단위였음 )
	   - Pod 안에 하나 이상의 컨테이너를 포함함. ( 일반적으로 하나의 컨테이너를 가짐 )
	   
	     https://kubernetes.io/docs/concepts/workloads/pods/
		 https://kubernetes.io/docs/reference/kubernetes-api/core/pod-v1/
  
     2. 특징
	   a. Pod 안에 하나 이상의 컨테이너를 포함함.
	   b. Pod 안에 있는 컨테이너들이 네트워크과 볼륨을 공유할 수 있음. (************)
	   
			--------------------------
			  pod 
			  
			   --------------
			    conainter1
			   --------------

			   --------------
				container2
			   --------------
			   
			   shared Network
			   shared Volume
			----------------------------------
			
		c. Pod는 일시적인 ( Ephemeral ) 객체임 (영구적인 객체가 아님 ) 
		  언제든지 제거될 수 있고 새로운 Pod가 생성될 수 있음.
			 ex.  Node 장애
			      Pod 삭제
				  Deployment 업데이트
				  Scale Out/In  ( 트래픽에 따른 Pod 갯수 증가/감소 )
				  
		  ==> Pod에서 했던 데이터 유지가 기본적으로 불가. ( 영속성을 위해서 Volume 사용함 )		 
		
		d. Pod는 직접 생성하기 보다는 다른 리소스를 이용해서 만드는것이 일반적임.
		   이유는 더 많은 기능이 포함됨.
			ex. Deployment, StatefulSet, Job, CronJob
		   
		   
		e.  Pod는 lifecycle 가짐.
		https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/
		
		     pending --> running --> succeeded/failed
			 
		  pending: Pod가 생성되었으나 아직 실행되지 않음.
		  running: 하나이상의 컨테이너가 실행중.
		  succeeded: 하나이상의 컨테이너가 모두 정상종료.
		  failed:   하나이상의 컨테이너가 비정상종료.
		  Unknown:  노드와 통신불가로 인해서 상태확인 불가.
		  
		  
		  확인방법:  kubectl get pods 
		  
		f. RestartPolicy 정책이 있음.
		  - Pod가 제거된 후 재시작과 관련된 정책임.
		  https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#example-scenarios
		  
		  
		   가. Always : 컨테이너가 종료되면 항상 재사작됨. 
		   나. OnFailure : 실패했을때만 재시작. 
		   다. Never   : 재시작하지 않음.
		   
		  
		g. image관련 정책 (  ImagePullPolicy )
 
     https://kubernetes.io/docs/concepts/containers/images/#image-pull-policy
	 
	        - Pod가 실행될 때, 컨테이너 이미지를 언제, 어떤 방식으로 hub에서 가져올지 결정하는 정책임.
	    
			- 3가지
			
			 가.  Always : 무조건 매번 hub에서 가져옴.( 사실은 아님 )
						   실제동작은 다음과 같다.
						   -hub에 이미지 확인을 요청함.
						    만약에 로컬에 없으면 새롭게 다운로드  되고
							있으면 캐시 이미지 사용.
			 
			 나.  IfNotPresent : Node(local)에 이미지막 없을때만 다운로드  ( 가장 많이 사용 )
			 
			 다.  Never  : 항상 로컬에 있는 이미지 사용.
		
		
		    - ImagePullPolicy를 생략했을 경우의 기본값.
			
			   가. tag가 latest 인 경우 
				- 기본적으로 Always로 동작됨.
			   
			   나. tag가 특정 버전인 경우 ( latest가 아닌 경우 )
			    - 기본적으로 IfNotPresent 동작됨.
				
		
			- ImagePullBackOff
			 https://kubernetes.io/docs/concepts/containers/images/#imagepullbackoff
			 
			  ==> K8s가 이미지를 가져오지 못하는 경우에 발생됨. 결국 컨테이너가 생성되지 못함.
			  ==> 원인: 이미지 이름 오타.
					    tag 오타

		 c. CrashLoopBackOff : 컨테이너가 계속 죽고 살아나는 동작을 반복함.

	5) Pod 내의 컨테이너에서 실행되는 어플리케이션(ex. SpringBoot) 로그 출력
	
	  https://kubernetes.io/docs/reference/kubectl/generated/kubectl_logs/
	  
	   - 개념: 컨테이너에서 실행되는 어플리케이션(ex. SpringBoot)의 정상로그(표준출력)와 오류로그(표준에러)를 출력하는 명령어.
	   
	   - 문법: 
	
	          kubectl logs [-f] [-p] (POD | TYPE/NAME) [-c CONTAINER]
	
				-f, --follow : 인텔리제이 로그처럼 실시간으로 로그 출력 가능.
				-c 컨네이너명:  컨테이너명 지정.
	            --tail n :     마지막 로그중 n개 출력.
				-l, --selector string : 필터링 
				--since 시간:  지정된 시간 이후 로그만 출력, ( 단위: 2s, 2m, 2h )
				--timestamps : 시간 출력
				-p, --previous : 재시작전 로그 출력.  ex. CrashLoopBackOff 발생시 필수로 봐야됨. 
		  ex. 
		      kubectl logs nginx-pod		
			  kubectl logs nginx-pod	--tail 10
              kubectl logs nginx-pod    --since=1m
			  kubectl logs nginx-pod   -c  nginx-container
			  
		==> 최종적으로 정리
		 
		     kubectl get : 상태 확인용.
			 kubectl describe: 이벤트 확인용
			 kubectl logs : 우리가 사용하는 어플리케이션(ex. Springboot, Vuejs ) 로그값 출력.

	   - 개념: label을 추가/수정/삭제/조회 하는 명령어

11)   빠른 pod 생성
 
   https://kubernetes.io/docs/reference/kubectl/generated/kubectl_run/
   
   -개념:  빠른 방법으로 pod 생성하는 명령어.
          실무에서는 yaml 이용.
		  
   - 문법:
        kubectl run NAME --image=image [--env="key=value"] [--port=port]
    		[--dry-run=server|client] [--overrides=inline-json] [--command] -- [COMMAND] [args...]
	  
		 --image : 컨테이너로 만들 base 이미지명.
		 --env   : 환경변수 
		 --port  : 문서화 기능 
		 --dry-run : 실제 생성하지 않고 YAML 확인가능.
	    --command : 명령어 지정
		-- 명령어:  컨테이너에서 실행할 명령어 지정
		--image-pull-policy:  ImagePullPolicy 정책.  Always, IfNotPresent, NEVER 
		--restart :  restartPolicy 정책.   Always, OnFailure, Never
		-it  : 표준입력과 모니터 활성화
		--rm : 종료시 자동삭제
		
	  ex. 
	   
	     kubectl run pod9 --image=nginx
		 kubectl run pod9 --image=nginx --dry-run=client  -o yaml  # 실행되지 않고 yaml로 출력됨.
		 kubectl run pod9 --image=nginx --restart=Never  --port=5701
		 kubectl run pod9 --image=nginx --env="DNS_DOMAIN=cluster" 
		 kubectl run -it pod9 --image=nginx -- bash
	     
		 kubectl run pod9 --image=nginx --rm

 7장   Pod 의 리소스 자원 (CPU/Memory) 관리 
 //////////////////////////////	
 
  https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#requests-and-limits

      1)개념: 여러 Pod들이 Node의 CPU와 Memory를 공유해서 사용함.
	        그런데 특정 Pod가 과도하게 CPU와 Memory를 사용하면 
			다른 Pod들이 문제가 발생될 수 있음. 따라서 CPU와 Memory 사용량에 대한 제한을 설정해야 됨.
			
	   
	        ---------------
			 Node (PC)
			 
			   ----
			   Pod (SpringBoot)  - 희망 자원: 최소한 이 정도의 CPU와 Memory가 필요해~ 
											 ex. CPU: 1 , Memory: 1Gi
											 
								 - 제한 자원: 최대한 사용할 수 있는 CPU와 Memory 크기 지정.
  								            ex. CPU: 2 , Memory: 3Gi
										만약 CPU를 초과하면 사용제한함( Throttling 발생)
										    Memory 초과하면 종료됨 ( OOMKill 됨 )
			   ----
			   
			   ---
			   Pod (MySql, Redis)
			   ---
			  
			 CPU 자원 ( I7 12Core )
			 Memory 자원 ( 32G )
			-------------------
			
	  2. 설정 방법
	  
		  spec:
		    containers:
			   resources:
				  requests: # 희망 자원
					memory: "64Mi"
					cpu: "250m"
				  limits:  #  제한 자원
					memory: "128Mi"
					cpu: "500m"
					
	 3. 단위 
	 
	     가. CPU 단위 ( MilliCPU )
		    - 1000m =  1CPU = 1 Core 
			
			  ex. 
			     100m = 0.1 CPU
				 250m = 0.25 CPU
				 500m = 0.5 CPU
				 1000m =  1 CPU
		  
		 나. Memory 단위
		  
		   - ki: kibi byte
		     mi: Mibi byte
			 Gi: Gibi byte
			 
			 
			 1ki = 1024byte
			 1Mi = 1024^2 byte
			 1Gi = 1024^3 byte
			 
			 ex. 
			    1Gi = 1024MB 
				128Mi = 128MB 
				
	 4. requests
	 
	     -개념:  최소 보장 자원 
		       ( 최소한 이 정도의 CPU와 Memory가 필요해~ )
			   
		 -용도: scheduler가 Pod를 어느 node에 올릴지 결정하는 기준이 됨.
		       중요한 것은 실제 실행했을 때 필요한 자원이 기준이 아님.
			   requests에 부합되지 않는 Node에는 배치안됨.
			   
			   
	5. limits
 
       - 개념: 최대 사용 자원 .
	   - 용도: 리소스(Pod) 보호.
	          특정 Pod가 자원을 독점하지 못하도록 제한함.
			  
	   -동작:
            CPU가 초과되면 Throttling 발생 ( 최대 상한선에서 사용되도록 강제 )
            Memory가 초과되면 강제 종료 발생 ( OOMKill 라고 부름 )

 6장  K8s 주요 객체 2 - Namespace
 //////////////////////////////

      https://kubernetes.io/docs/concepts/overview/working-with-objects/namespaces/
      https://kubernetes.io/docs/reference/kubernetes-api/core/namespace-v1/
	  
	  1.개념
	   - 하나의 K8s의 클러스터를 논리적으로 여러개 분리해서 관리하는 기능임.
	  
	  2. 목적
	   - K8s의 클러스터에 있는 여러 리소스들을 용이하게 관리하기 위함.
	    (자바의 패키지 기능과 비슷)
		
		
	 3. 특징 
	   - 하나의 리소스는 하나의 Namespace에 속함.
	   - 같은 Namespace 안에서는 리소스 이름이 유일.
	     Namespace가 다르면 리소드 이름이 중복 가능.
	   - default Namespace가 제공됨.	 
	   - 모든 리소스가 Namespace를 사용할 수 있는 것은 아니다.
		  Namespace 적용가능한 리소스: Pod, Serivce,Deployment,ReplicaSet, ConfigMap, Secret,
                            		  PVC(PersistentVolumeClaim)
									,StatefulSet
									Job, CronJob, Ingress
									
		  Namespace 적용 불가능한 리소스(클러스터 단위): Node, Namespace, PV(PersistentVolume)
		 
		==> 확인방법:  kubectl api-resources 에서 NAMESPACED 항목을 확인하면 됨.
		
	  - Namespace를 삭제하면 그 안에 있는 리소스(pod, service 등)들도 같이 삭제가됨.(*******************)
	  - 리소스를 조회할 때, 반드시 Namespace 명을 지정해야 됨. 
	     ex. kubectl get pods                 # default Namespace에서 찾음.
		     kubectl get pods -n 네임스페이스명 #  지정된 Namespace에서 찾음.
			 
	  - 자동으로 제공되는 Namespace가 있음.
	    ex. kube-node-lease, kube-public , kube-system
	    
	 4. Namespace 관려 주요 명령어.

 6장  K8s 주요 객체 3 - ReplicaSet
 //////////////////////////////
 
     https://kubernetes.io/docs/concepts/workloads/controllers/replicaset/ 
	 https://kubernetes.io/docs/reference/kubernetes-api/apps/replica-set-v1/
 
    1. 개념
     - 지정한 갯수만큼 Pod를 생성해주는 리소스.
	   만약에 하나의 pod가 장애로 인해서 종료되면, current state와 desired state 비교해서 
	   desired state 상태로 만듬.
	 - ReplicaSet 삭제하면 관련된 Pod 들도 같이 삭제됨. 
	 
	2. 목적
      - pod 갯수 유지 ( desired state 유지 )
	  - 고가용성 보장
	  
	3. ReplicaSet의 yaml 구성.
	
		 샘플:
		 
		    apiVersion: apps/v1  # API Version.  kubectl api-resources  확인 가능.
			kind: ReplicaSet
			metadata:
			  name: frontend     # ReplicaSet 이름 
			  labels:			 # Label 지정 
				app: guestbook
				tier: frontend
			spec:
			  # modify replicas according to your case
			  replicas: 3		 # Pod 개수, desired state 임.
			  
			  selector:			 # 접근하고자 하는 리소스 찾을 때 사용하는 속성
				matchLabels:
				  tier: frontend #  tier: frontend 형태로 된 label을 찾음. (*******************)
				  
				  
			  template:   # ReplicaSet이 만들어야 되는 Pod 정보 지정하는 영역.
				metadata:
				  labels:
					tier: frontend #  tier: frontend 형태로 마킹. (*******************)
				spec:
				  containers:
				  - name: php-redis   # 컨테이너이름
					image: us-docker.pkg.dev/google-samples/containers/gke/gb-frontend:v5 # Pod의 base이미지명

	    ==> selector.matchLabels의 값과 template.metadata의 값과 반드시 일치해야 된다. (*******************)

    실습 5> ReplicaSet으로  특정 pod 제외.
	
	  https://kubernetes.io/docs/concepts/workloads/controllers/replicaset/#isolating-pods-from-a-replicaset
	  
	  
	   개념: ReplicaSet이 관리하는 Pod로부터 제외시키는 방법.
	   용도: 제외시켜서 디버깅용으로 활용 가능. 
	   방법: 실행중인 Pod의 라벨을 변경하면 제외됨.
	   
	   
	   
	    1) label 수정
		
		    kubectl get pods
				NAME           READY   STATUS    RESTARTS   AGE
				rs-pod-4kfmg   1/1     Running   0          17m
				rs-pod-qpj8b   1/1     Running   0          17m
				rs-pod-zc2vb   1/1     Running   0          10m
		
		    kubectl label pods rs-pod-4kfmg	 app=web2 --overwrite   # app 라벨 수정 
	  
	    2) 확인 
		
		    kubectl get pods  --show-labels
			   NAME           READY   STATUS    RESTARTS   AGE   LABELS
				rs-pod-4kfmg   1/1     Running   0          46m   app=web2   # replicaSet이 관리안함.
				rs-pod-6gd88   1/1     Running   0          8s    app=web
				rs-pod-qpj8b   1/1     Running   0          46m   app=web
				rs-pod-zc2vb   1/1     Running   0          39m   app=web
				
				
	    3) 모두 삭제. 

		   kubectl delete rs --all   # ReplicaSet 삭제하면 관리하고 있는 pod도 모두 삭제됨 .
		   
		   kubectl delete rs rs-pod	--cascade=orphan  # ReplicaSet 삭제하면 관리하고 있는 pod 삭제 안됨 .

 6장  K8s 주요 객체 4 - Deployment (**************)
 //////////////////////////////	  
	  
	  https://kubernetes.io/docs/concepts/workloads/controllers/deployment
	  
	  1. 개념 
	  - Pod 와 ReplicaSet 기능을 포함 및 추가 기능을 지원하는 리소스.
	  
	  2. 추가 기능 
	  
	    - pod 자동복구
		- 버전관리 지원 ( template 태그쪽 수정해야 버전(이력)으로 남음 )
		- 롤백 (특정 버전으로 돌아갈 수 있음)
		- 무중단 업데이트 가능 (롤링 업데이트(Rolling-update)라고 부름)
		  ex. 기본 Pod를 일부분 삭제하고 , 새로운 Pod를 일부분 생성하면서
		      전체를 새로운 Pod로 업데이트하는 방법임.
			  따라서 서비스 중단이 없음.
	    - scaling 가능.
	  
	  3. 기본 Deployment yaml 
	  
	  https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#creating-a-deployment
	  
	    apiVersion: apps/v1
		kind: Deployment
		metadata:
		  name: nginx-deployment   # Deployment이름
		  labels:				  # 라벨 이름
			app: nginx
			
		spec:
		  replicas: 3
		  selector:
			matchLabels:
			  app: nginx     #  (*********************)
			  
			  
		  template:             # Deployment 내의 ReplicaSet이 관리한 Pod 정보
			metadata:
			  labels:
				app: nginx    #  (*********************)
			spec:
			  containers:
			  - name: nginx
				image: nginx:1.14.2
				ports:
				- containerPort: 80
				
          ==> selector.matchLabels의 값과 template.metadata의 값과 반드시 일치해야 된다. (*******************)

	  4. Pod 교체 전략 
	   
	     1) 개념 
		   - K8s의 Pod를 교체하는 방법의미. 
		   
		 2) 2가지 방법 
		 
		  가. 롤링 업데이트 방식 (Rolling-update)- 기본동작
		      - 방법: 구버전 Pod를 삭제, 신버전 Pod를 생성하면서 업데이트 하는 방식.
			  - 장버: 서비스 중단 없음.(무중단 배포 가능)
			    단점: 배포 시간이 길어짐.
			         버전들이 혼재함.
			  
			   -샘플:
					 replica: 10
					 
		             strategy:
						rollingUpdate:
						  maxSurge: 3
						  maxUnavailable: 2
						type: RollingUpdate
						
			https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#proportional-scaling	참조.
			
			 - maxUnavailable : 업데이트 중에 삭제할 수 있는  pod 비율 
			 - maxSurge : replicaset 보다 추가로 더 만들 수 있는 pod 비율 
			
			--------------------------------------------------
			   replica: 10
			   maxSurge: 3
			   maxUnavailable: 2
			
			step1: 새로운 Pod 3개 생성
			
					 구버전: 10

					 총: 13개 (maxSurge)
			
			step2:  구버전 2개 삭제가됨
			      
				     구버전:8
					 신버전:3
					 
					 총: 11개 (maxUnavailable)
			
			step3: 새로운 Pod 2개 생성
			
					 구버전:8
					 신버전:5
					 
					 총: 13개 (maxSurge)
					 
			step4:  구버전 2개 삭제가됨		 
					 
					 구버전:6
					 신버전:5
					 
					 총: 11개 (maxSurge)
					 
			step5: 새로운 Pod 2개 생성		 
					 
					  
					 구버전:6
					 신버전:7
					 
					 총: 13개 (maxSurge)
					 
			step6:  구버전 2개 삭제가됨		 
					 		 
					 구버전:4
					 신버전:7
					 
					 총: 11개 (maxSurge)
					 
					 
			step7: 새로운 Pod 2개 생성	
                    
					 구버전:4
					 신버전:9
					 
					 총: 13개 (maxSurge)	

			step8:  구버전 2개 삭제가됨	

                     구버전:2
					 신버전:9
					 
					 총: 11개 (maxSurge)		

            step9: 새로운 Pod 1개 생성 # 최종 신버전 갯수가 10가 필요하기 때문에 1개만 새로 생성됨 .

					  구버전:2
					 신버전:10
					 
					 총: 12개 (maxSurge)	  
					 
			step10:  구버전 2개 삭제가됨		

                     구버전:0
					 신버전:10
					 
					 총: 10개 (maxSurge)	  			
			---------------------------------------------------
			 
		  
		  나. 재생성 방식 
		    - 개념: 구버전 pod를 모두 삭제하고 나중에 신버전 pod 생성.
			- 장점: 배포시간이 짧음. / 버전충돌 없음.
			  단점: 서비스 중단 발생 ( downtime 발생됨 )

 7장  K8s 네트워크 
 //////////////////////////////	
 
    1. 개념
	   - 클러스너내의 모든 pod를 하나의 네트워크로 묶어서 관리하는 구조.
	   - Node단위가 아닌 클러스터 단위의 네트워크임.
	     즉, Node 위치와 무관함.( NAT,Port forward 등 추가 기능이 필요없음 )
	     
	   --------------------------------------------------------------------
	    가능한 이유?
	    쿠버네티스는 CNI 플러그인이 노드 간에 VPN과 유사한 터널링을 구성하기 때문에,
		물리적으로 다른 네트워크에 있는 파드끼리도 사설 IP로 직접 통신이 가능하다고 합니다.
		제가 이해가 안되었던 부분은 별도의 라우팅 설정 없이 어떻게 서로 다른 네트워크 간 통신이 가능한지였는데, 
		CNI가 터널링으로 오버레이 네트워크를 구성해서 하나의 가상 네트워크처럼 동작하기 때문이라고 합니다. 
		
		아래 터널링 방식을 이용해서 통신한다고 하네요. (Cilium)
       All cluster nodes form a mesh of tunnels using the UDP-based encapsulation protocols VXLAN or Geneve. 
		https://docs.cilium.io/en/stable/network/concepts/routing/
	   --------------------------------------------------------------------------------------

 6장  K8s 주요 객체 5 - Service
 //////////////////////////////	 	    
 
 https://kubernetes.io/docs/concepts/services-networking/service/
 
 
    1. 개념 
	 - Pod는 외부에서 직접 접근이 불가능하기 때문에 Service를 통해서 POd에 접근할 수 있음.
	 
	2. 용도 2가지

      1) Pod를 외부에서 접근하도록 하기 위함.

      2) Pod와 Pod 간 연동할 때, Pod IP는 변동될 수 있기 때문에 고정된 값을 가진 Servic를 사용함.	  
	  
	3. 역할 
	  
	   1) 고정 IP 역할 
	   2) DNS 제공                      K8s의 CoreDNS 
	      ex. http://hello-service ----------------------------> IP 번호 
	   3) 로드밸런싱 역할
	
	4. Service가 Pod  선택 
		
		# service Yaml 샘플 
	       
		    apiVersion: v1             # API Version
			kind: Service              # 리소스 종류 
			metadata:
			  name: my-service        # 서비스 명 
			spec:
			  selector:
				app.kubernetes.io/name: MyApp  # app.kubernetes.io/name: MyApp 값으로 설정된 
			  									 label를 가진 Pod 선택. ( 여러 Pod tjsxor rksmd )
			  ports:
				- protocol: TCP
				  port: 80				# Service 의 port 번호 
				  targetPort: 9376      # Service가 접근하는 Pod의 port 번호 
			  
			  type: ClusterIP
	
	   가. pod ( label 이용 )
		
			 labels:
			    x: y
	   
	   
	   나. Service ( selector 이용 )
	   
	        spec:
			  selector:
				x: y

    1. 개념 
	  - 클러스터 외부에서 들어오는 트래픽을 호스트 정보 및 경로 정보를 활용해서 
	    특정 Service로 라우팅 해주는 K8s 리소스임.
	    
		요청URL(경로로 구분) :   http://localhost:80/app1     -----------> app1-service 로 라우팅 
                               http://localhost:80/app2    -----------> app2-service 로 라우팅 

        요청URL(호스트로 구분) :  http://a1.service:80     -----------> app1-service 로 라우팅 
                               http://a2.service:80    -----------> app2-service 로 라우팅    

							   
	2. 구조 
	
	   
						                        외부 ( 웹브라우저 ) 요청: http://localhost:80/web
												                      http://localhost:80/web2
	
               --------------------------------------------------------------------------- 클러스터
													  |
													 Ingress  (스펙,interface)

			kind: Ingress					  # 리소스
			metadata:
			  name: minimal-ingress           # Ingress 리소스 명 
			spec:
			  ingressClassName: nginx-example # Ingress Controller 이름. 
												현재 설치된 NGINX Ingress Controller의 name값이 nginx임.
												따라서 nginx로 지정하면 됨. 
												kubectl get ingressClass 에서 name 확인 가능.
												
			  rules:                     # 경로규칙 
			  - http:			         # http 라우팅 규칙임.( host(ex. xxx.example.com )없이 경로만 규칙에 포함)
				  paths:
				  - path: /testpath     # 경로  http://xxx.example.com/testpath
					pathType: Prefix    # 종류
											 Prefix: 접두어만 일치하며 됨. 즉 /testpath 로 시작하면 됨.
											 Exact: 경로가 정확하게 일치해야됨. 
											 ImplementationSpecific: Ingress Controller에 따라서 Exact 또는 Prefix로 동작됨.
											  현재 설치된 NGINX Ingress Controller는 Prefix 동작됨
						
					backend:
					  service:
						name: test      # 서비스명 
						port:
						  number: 80    # 서비스 포트

		         - path: /testpath2     # 경로
					pathType: Prefix
					backend:
					  service:
						name: test2

						  number: 80

     1)개념 
	    - 컨테이너안 어플리케이션이 실행될 때 참조하는 설정값.
		
		가. SpringBoot ( external Configuration )
		
		   - application.yaml 에서 환경변수 설정 
		   
		       ex.  server: 
			           port: 80 
		
		   - 사용
		       - @Value("${server.port}") ( 한번에 하나씩 참조 )
			     String port; 
		      
			   - ConfigurationProperties ( 한번에 여러 환경변수 참조 )
		
		   - 언제든지 환경변수 동적으로 수정이 가능 
		   
		       java -jar  app.jar  --server.port=8090 # 커맨드 라인 아큐먼트 ( 우선권이 가장 높음 )
		
		나. Docker 
		 
		  - Dockerfile에서는 ENV 사용 
		  
		      ex. 
			       FROM eclipse-temurin:21-jre

					WORKDIR /app

					COPY build/libs/*.jar app.jar

					ENV SERVER_PORT=8080
					ENV APP_NAME=spring-env-demo
					
		  - 실행시 env 사용 
		  
		     a.    -e, --env 옵션 이용 ( 우선권이 가장 높음 )
			  
			     ex. docker run -e key=value  -e key1=value1  이미지명
			 
			 b.   --env-file 이용
			 
			    docker run --env-file=.env  이미지명
				
		 - 사용 
		 
			쉘에 접속해서 
			docker exec -it nginx-container -- bash
			root> env 
			      printenv 
				  echo $SHELL

		   1)개념

			        apiVersion: v1
					kind: Pod
					metadata:
					  name: print-greeting
					spec:
					  containers:
					  - name: env-print-demo
						image: bash
						env:
						- name: GREETING    # name(key)는 대문자 권장 
						  value: "Warm greetings to"
						- name: HONORIFIC
						  value: "The Most Honorable"
						- name: NAME
						  value: "Kubernetes"
						- name: MESSAGE
						  value: "$(GREETING) $(HONORIFIC) $(NAME)"   # 다른 env 참조 가능. $(name), 소괄호
						command: ["echo"]
						args: ["$(MESSAGE)"]
